# 人とAIが参加する通話の境界

**Status**: partial — 参加者・承諾・退出のローカル状態モデルから実装。通信、AI接続、複数アバター表示、プロファイル分離は未実装。
**Last updated**: 2026-09-12

## TL;DR

同じPCの複数AIと別PCのAIを共通の通話参加者として扱い、人も任意に参加できる。
通話セッションをUI・通信方式・個々のAI実行セッションから分離する。
dev / releaseで記憶を自動分割せず、複数起動の検証にだけ明示的なテストプロファイルを用意する。

## 何を決めたか

### 参加者と接続先

「人かAIか」と「どの端末・アプリが所有するか」を別々に保持する。同じ接続先から複数のAIや人が参加できる。local / remote は現在のアプリから見た位置関係であり、受信者が決定する。相手から送られた `local` という自己申告を権限の根拠にしない。

参加者の承諾・在席・権限は通話セッションの寿命に閉じる。招待を作っただけでは参加・メディア送信を許可しない。退出・終了でその入室に対応する許可を失効させ、再入室には新しい承諾を必要とする。遅延した前回の参加操作で許可を復活させない。

最初の実装はhost所有のメモリ内状態モデルに限定する。外部から受信したメッセージを直接このモデルの操作として適用してはいけない。認証、所有者確認、招待の期限・失効、シグナリングの順序検証は通信アダプターを実装する時の別の責務となる。

### 表示とAI実行

ホストが部屋を作ってシーンを選び、人やAIを招待する。部屋のシーン・参加者・アバター配置・共有内容は共通の状態とし、シーン変更は最初はホストの操作として設計する。表示モードと個々の視点は各クライアントの状態にする。ホストがシアターでも参加者はコール/ポートレートを選べる。これは部屋同期の設計方針であり、今回の参加者モデルにホスト権限やシーン同期はまだ含まれない。

同じ通話を、シアターでは共通シーン、コールでは参加者別の枠、ポートレートでは一人ずつの縦長枠で表示する。画面共有時は共有内容を主表示にできる。モード切替で通話を再作成しない。受話器ボタンは画面共有の隣を基本とするが、生成画像のレイアウトや参加者パネルは仮案。

既存UI pack ID `portrait` が表示名 Call、`companion` が表示名 Portrait。表示名だけからIDを推測しない。

既存のsingle-active persona registryをそのまま複数activeに変えない。複数の独立AIセッションと、それぞれのアバター表示を通話層で関連付ける。1台で複数AIを実行する機能も正式な対象とし、単なる別PC通話のテスト代替には限定しない。

AIの入力・発話・停止・利用量の上限はAI参加アダプターが所有する。発話者と発話IDを管理し、自分の声への反応、応答の重複、無制限のAI同士の応酬を防ぐ。人の割り込みと一括停止を扱う。通話の発言からPTYへ入力する経路は作らない。

### 記憶の継続と検証用プロファイル

保存先の選択はbuild種別から独立させる。普段のよりしろをdev版で動かしても、その記憶を継続できることを守る。検証用の別参加者が必要な時にだけ、新規のテストプロファイルを明示して起動する。通常の記憶・認証情報・実行中セッションをテスト側へ自動コピーしない。

アプリインスタンス、検証用プロファイル、AIの人格・記憶、通話セッションは別概念。同じプロファイルを使う複数プロセスによる同時書込みを許すかは別途設計し、最初の検証では同一保存先への複数writerを避ける。worktreeだけではランタイムの保存先は分離されない。

`HOME`や`CODEX_HOME`を置き換えて分離しない。Yorishiro専用の明示的な保存先設定と、アプリ識別子・WebView保存領域・開発用ポートの組合せで分離する。起動時に通常のグローバルskill設定を書き換える処理も、検証用プロファイルでは分離または抑止する。

## なぜそう決めたか

| 現行箇所 | 意味 |
|---|---|
| `src/runtime/three-runtime/`、`src/vrm-viewer.tsx` | 一つのVRM・Body・camera・canvasを共有。Viewerを二つ置くだけでは複数アバターにならない |
| `src/runtime/codex-realtime/use-screen-sharing.ts` | 画面/カメラを画像としてAIに観察させる経路。参加者への動画配信とは別 |
| `src/runtime/persona-registry/` | single-activeな主AIの人格選択。通話参加者の一覧ではない |
| `src-tauri/src/lib.rs` のhome・history・plugin準備 | 設定・記憶・復元・runtime pluginなどに共通保存先と直接参照が残る |
| `src-tauri/src/attach/transport.rs` | attach socketは保存先ごとに一つ。2プロセス目のattach listenerは競合する |
| `src-tauri/src/mcp/server.rs`、`src-tauri/src/pty.rs` | MCPは動的ポートへのfallback、hookは動的ポートとインスタンス別tokenがある |
| `src-tauri/tauri.conf.json`、`vite.config.ts` | 識別子と開発URLは固定。アバターimport先はTauri app data、UI状態の一部はlocalStorage |

ネットワーク・描画・検証用データ分離を一度に既存singletonへ載せず、参加者とセッションの契約を先に検証する。

## セキュリティ上の制約

- 通話用の限定された通信経路を新設し、既存のローカルMCP・PTY・Tauri IPCを相手PCへ公開しない。
- 相手のアバターやシーンをtrusted local packとして自動インストール・実行しない。初期検証は手元のサンプルアセットを使う。
- 音声・画面・カメラを人に共有する許可と、AIモデルサービスへ入力する許可を分ける。入室承諾だけでAIへの外部転送を一括許可しない。
- E2EEの対象をメディア/字幕/状態ごとに定義する。クラウドAIへ入力を渡す時は、そのAI提供者が内容を処理することを表示・説明する。端末間E2EEがあってもこの事実は変わらない。
- 私的な履歴・記憶・内部プロンプトを自動公開しない。通話の発言は権限の低い入力として扱い、ローカル操作権限へ昇格させない。
- 退出・共有停止・切断による許可失効をAI入力とメディア配信にも伝える。状態モデルだけでは送信停止は成立しないため、アダプターの中断・トラック停止を結合テストする。

## 検討したが採らない案

- **devとreleaseで常に記憶を分ける**: buildを替えた時に普段の住人との継続性を失う。明示的な検証用プロファイルを採る。
- **同じPCなら無条件に参加を許す**: AIの所有者・入力範囲の違いが消える。localでも参加と共有を明示する。
- **ローカルMCPを外向きに公開する**: 通話に不要なローカル操作を公開し、既存の信頼境界を壊す。
- **受信したパックをそのまま実行する**: 現行packはアプリと同じ権限を持つローカルコードであり、通話相手の表現データとして扱えない。
- **生成画像を完成UIとして実装する**: ユーザーは見せ方を継続検討中。セッションとレイアウトを独立させる。

## 実装順

1. 参加者・承諾・入室・退出・失効の状態モデルを追加し、古い操作で参加権限が戻らないことを検証する。
2. 明示的な検証用プロファイルに対し、保存先・plugin準備・attach・WebView・開発ポートを分離する。通常プロファイルとテストA/Bの書込み・復元・終了の独立性を検証する。
3. 2体のアバター表示と複数AIの独立セッションをローカルで検証し、共通参加者モデルへ接続する。
4. 別PC間の通信方式を実測で選び、招待・認証・権限・暗号化を含む縦通しを作る。受話器ボタンはこの接続へつなぐ。
5. シアター/コール/ポートレートの切替、画面・カメラ共有、多人数時の発話制御を追加する。

通信サービス、最大人数、AI提供者ごとの参加方式、アセット配送、記録の既定値、UI細部は未確定。ホスト退出時の終了/権限移譲も部屋同期の実装前に決める。通信方式の判断にはTauri上の実機検証を含める。
